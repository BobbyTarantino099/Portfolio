Arquitectura del portafolio

Cómo está construido este portafolio: sus repositorios, su stack, cómo viajan los datos desde un CSV de 383 MB hasta una página que carga en un teléfono, y el framework que produce el contenido.

Documentación técnica de referencia · Uso interno, no publicada
Versión 1 · 11 de agosto de 2026 · Estado del sistema verificado en esa fecha

1. Qué es esto y cuándo actualizarlo

Este documento existe para que dentro de seis meses puedas volver a entender tu propio sistema sin reconstruirlo leyendo código. No es material para reclutadores — eso ya lo cubre la página /method del sitio, escrita en inglés y para otra audiencia. Este está en español porque es una herramienta de trabajo, igual que el framework.

Se regenera cuando cambia la arquitectura, no cuando cambia el contenido. Tres disparadores:

DisparadorQué invalida
Cambio de stack o infraestructura Versión mayor de Astro, cambio de hosting, mover el dominio, añadir un adaptador de servidor. Los diagramas de la sección 3 dejan de ser ciertos.
Cambio en el contrato o el esquema Añadir o quitar campos del front-matter, cambiar el orden fijo de secciones, tocar src/content.config.ts. Es el corazón de cómo entra un caso al sitio.
Cambio en las fases o reglas del framework Añadir una fase, mover una puerta de salida, reescribir una regla dura. El framework es la mitad de lo que este documento describe.

Publicar un caso nuevo no dispara una actualización. Eso es deliberado y es la prueba de que el sistema funciona: si meter el caso 4 obligara a redibujar la arquitectura, significaría que el contrato de contenido no está haciendo su trabajo. El día que publicar un caso sí exija tocar este documento, el problema no es el documento.

2. Vista general

El portafolio son dos repositorios y una regla. Un repositorio contiene el sitio y el framework que lo gobierna; el otro contiene la evidencia completa de un caso de estudio — y habrá uno por caso. La regla es que los datos pesados nunca cruzan del segundo al primero: solo lo hacen agregados de kilobytes.

El sitio es estático. No hay servidor, ni base de datos, ni CMS. Escribir un caso es escribir un Markdown; publicarlo es hacer git push.

4. Arquitectura de datos

Una sola regla ordena todo: el sitio solo transporta agregados. Los datos crudos y los derivados intermedios se quedan en el repositorio del caso, fuera del control de versiones, y se regeneran ejecutando los scripts.

Regla dura. Los datos crudos jamás se modifican en su sitio. Toda transformación produce un archivo nuevo y queda anotada en la bitácora de limpieza. Es lo que permite que un tercero clone el repositorio, descargue el crudo original y reconstruya el análisis entero.

5. Modelo de publicación en tres capas

El framework aplica divulgación progresiva a cómo se lee la documentación. La misma idea gobierna cómo se publica: tres capas, tres audiencias, tres tiempos de lectura. Nadie lee un CASO.md de 460 líneas en una web — pero quien quiere ese nivel de detalle sabe dónde buscarlo, y encontrarlo completo es justo lo que separa un caso defendible de una galería de gráficos.

6. El contrato de contenido

Es la pieza que hace que publicar el caso siguiente no obligue a rediseñar nada. Cada caso entrega un Markdown con front-matter, y el sitio lo valida contra un esquema Zod en src/content.config.ts. Si falta un campo obligatorio, npm run build falla — no se publica una página a medias.

---
title:        # EL HALLAZGO, no el tema
summary:      # 2-3 frases -> el párrafo de la tarjeta L1
hero:         # ruta a la visualización principal
heroAlt:      # texto alternativo real
date:         # AAAA-MM-DD
tools:        # [Python, pandas, matplotlib]
domain:       # sector del caso
problemType:  # taxonomía de la fase 1 (enum: 6 valores)
scale:        # "125,855 games · 2 sources"
repo:         # URL de la evidencia — OPCIONAL a propósito
featured:     # true -> aparece en la home
demonstrates: # qué demuestra frente a los demás casos
---

Y el orden de secciones es fijo: Context → Data → Process → Findings → Recommendations → Reproduce → What this demonstrates. No es rigidez decorativa; es lo que hace que abrir el caso 5 se sienta igual que abrir el caso 1.

Por qué repo es opcional. Si fuera obligatorio, no se podría publicar la página de un caso hasta tener su repositorio público — y eso encadena dos etapas que no tienen por qué depender la una de la otra. La puerta de salida del framework sí lo exige para dar un caso por terminado, pero eso lo revisa una persona, no la construcción.

7. El framework que produce el contenido

caso-de-estudio-datos son 19 archivos Markdown que viven en site/framework/, versionados junto al sitio. Adaptan el proceso de análisis del certificado Google Data Analytics y le añaden lo que lo hace repetible: cada fase tiene una puerta de salida que hay que pasar punto por punto antes de avanzar.

Divulgación progresiva

El framework no se carga entero de golpe: SKILL.md siempre, el archivo de la fase actual, el anexo de la herramienta cuando toca, y las plantillas al escribir el entregable. Cargar los quince archivos de referencia a la vez degrada la calidad de las respuestas y desperdicia contexto.

Un repositorio por caso, más uno para el sitio. Así cada caso es navegable por sí solo —que es donde miran los reclutadores técnicos— y el repositorio del sitio no carga con notebooks ni datos.

9. Cómo se publica un caso, de principio a fin

  1. Se recorre el framework, fase por fase, pasando cada puerta de salida. El artefacto vivo es CASO.md, que se actualiza al cerrar cada fase.
  2. Los scripts producen las figuras y las tablas agregadas en salidas/.
  3. Se escribe el Markdown de la capa L2 siguiendo la plantilla 7 del framework, con su front-matter completo.
  4. Ese Markdown y sus figuras se copian a site/src/content/cases/<slug>/.
  5. npm run build valida el contrato. Si falta un campo, falla aquí y no en producción.
  6. git push. Cloudflare construye y despliega en unos dos minutos.
  7. El repositorio del caso se publica y su URL entra en el campo repo.

Antes de publicar cualquier repositorio, se busca literalmente si quedaron rutas absolutas dentro del código:

grep -rn "/home/\|/Users/\|C:\\\\\|/sessions/\|/mnt/" \
     --include="*.py" --include="*.js" --include="*.ipynb" --include="*.md" .

Un script con la ruta de la máquina donde se escribió no es reproducible por nadie, y es lo primero que rompe cuando alguien clona el repositorio para comprobar tu trabajo.

10. Decisiones que conviene no re-litigar

DecisiónRazón
Sitio solo en inglés, sin i18n El mercado objetivo es remoto. Bilingüe duplicaría el trabajo de escritura de cada caso para siempre.
El framework se queda en español Es la herramienta de trabajo, no el producto. Lo que se publica va en inglés.
Workers, no Pages Pages está en mantenimiento; Cloudflare dirige los proyectos nuevos a Workers.
Un repositorio por caso Cada caso es navegable por sí solo en GitHub, que es donde mira un revisor técnico.
Gráficos estáticos por defecto Cero JavaScript, carga instantánea en móvil. La interactividad se añade solo cuando un caso concreto la justifica, no por defecto.
Los binarios se generan con scripts build_docx.py y build_pptx.js permiten regenerar el resumen ejecutivo y la presentación cuando cambia el contenido. Editarlos a mano los convierte en artefactos huérfanos.
